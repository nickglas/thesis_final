Unfortunately,   cloud-assisted   DNN   in- ference approaches may result in unpredictable communication latency caused by the long wide-area massive data transmission between devices and the cloud server [7,14]. To alleviate the above problems, it is naturally required to pro- mote the cooperation of end devices, edge servers, and the cloud server, called end–edge–cloud collaborative computing. In this computing paradigm, DNN computations are partitioned between end devices, edge servers, and the cloud server for collabora- tive execution. This collaborative computing paradigm combines cloud computing with high computing capacity and edge com- puting with low transmission latency [7]. Therefore, the time of DNN inference is further reduced.  1.2. Challenges  However, accelerating DNN inference with end–edge–cloud collaborative computing still faces the following two challenges. The first challenge is computation partitioning, which is the basis of collaborative computing [14,16]. Most of the existing computation partitioning approaches are cloud-assisted DNN in- ference [17] and edge-assisted DNN inference [18], which mainly use one partitioning point to divide DNN computations into end devices and the cloud server or into end devices and edge servers. Unfortunately, both these two approaches may lead to poor per- formance (i.e., high end-to-end latency) [6] A comparison of the one-point partitioning mechanism and two-point partitioning mechanism is illustrated in Fig. 1. The best partition point is pool5, which means executing the AlexNet on the end device up to that layer and executing the remaining layers on the cloud server. Obviously, the two-point partitioning mechanism is more efficient than the one-point partitioning mechanism in the end–edge–cloud computing platforms. Another challenge is per-layer latency prediction, which refers to accurately predicting the execution latency of each layer in a DNN before computation partitioning. Most of the existing prediction approaches [19,20] rely on linear models to estimate each layer’s execution delay. Nevertheless, the prediction accu- racy is highly related to the computing platforms and the DNN topology. Compared with the end–edge or end–cloud comput- ing platforms, end–edge–cloud computing platforms make the prediction process more difficult due to complex heterogeneity. Therefore, a more efficient prediction model will be needed for better prediction performance.  1.3. Contributions of the work  Inspired by these observations, in this paper, we propose an adaptive DNN inference acceleration framework to reduce DNN inference latency with end–edge–cloud computing, which adaptively partitions DNN computations into end devices, edge servers, and the cloud server for executions based on layer pre- diction results. Specifically, the main contributions of this article are summarized as follows:  •   Build latency prediction models to estimate the layer-wise execution latency of a DNN on different heterogeneous com- puting platforms, which uses neural networks to learn non- linear features related to inference latency for better predic- tion performance.  •   Design a computation partitioning algorithm to identify two optimal partitioning points, which divides DNN computa- tions   into   three   blocks   (i.e,   data-intensive   block,   hybrid block,   and   computation-intensive   block)   for   accelerating DNN inference across end devices, edge servers, and the cloud server.  •   Conduct extensive experiments on three widely-adopted DNNs to evaluate the effectiveness of the DNN inference acceleration framework. The experimental results show that the proposed framework can greatly reduce DNN inference latency compared with the five baseline approaches. The rest of this paper is organized as follows. Related work  Collaborative DNN inference approaches have been exten- sively studied, which can be roughly classified into cloud-assisted DNN inference [20], edge-assisted DNN inference [6], and collab- orative end–edge–cloud DNN inference [14].  Cloud-assisted DNN inference   refers to a collaborative com- puting approach, which partitions DNN computations into end devices and the cloud server for accelerating DNN inference. Kang et al. [20] studied the computing and data properties of 8 neural network-based intelligent applications and proposed a system to reduce t DNN inference delay. Baccarelli et al. [21] considered both the supervised training and energy-efficient of the Condi- tional DNNs (CDNNs) with early-exits. A greedy-based algorithm was proposed to place the early exits on the CDNNs. Eshratifar et al. [10] proposed an efficient engine for collaborative computa- tion between end devices and remote cloud, where an algorithm based on the integer linear programming (ILP) was developed to minimize inference delay and mobile energy consumption. Duan et al. [22] proposed a binary-search-based algorithm to select the best partitioning point between end devices and the cloud to maximize the performance of DNN inference. Baccarelli et al. [23] considered the model early-exit to make a good balance between accuracy and delay. A Learning-in-the-Fog (LiFo) framework was designed to minimize energy and maximize DNN inference ac- curacy. Eshratifar et al. [24] design a optimal task offloading approach to reduce the inference latency and mobile energy con- sumption while satisfying latency needs, in which both inference time and mobile energy consumption were considered. Baccarelli et al. [25] suggested a task offloading scheme for joint optimiza- tion of the resource allocation and task offloading in 5G, where an ad-hoc-developed Genetic algorithm was proposed to reasonably allocate resources and reduce the energy consumption of end devices. However, these works are highly susceptible to data transmission latency between end devices and the cloud server. Bandwidth congestion may incur unstable data transmission and then result in high response latency.  Edge-assisted DNN inference   refers to a collaborative com- puting approach, which divides DNN computations into end de- vices and edge servers for execution. Li et al. [6] considered  423

Framework design  The adaptive DNN inference acceleration framework is shown in Fig. 2, which consists of three stages, namely the prediction stage, partitioning stage, and collaborative inference stage.  At the prediction stage , this framework trains latency predic- tion models to estimate layer-wise inference latency of DNNs on three heterogeneous computing platforms (i.e., end devices, edge servers, and the cloud server). The latency prediction results are the basis for DNN computation partitioning.  At the partitioning stage , this framework uses a compu- tation partitioning algorithm to divide DNN computations into three   blocks,   namely,   data-intensive   block,   hybrid   block,   and computation-intensive   block.   This   algorithm   searches   for   the two best partitioning points by jointly considering layer-wise prediction results and the dynamic network condition.  At the collaborative inference stage , this framework offloads the hybrid block and the computation-intensive block to the edge server and the cloud server for inference acceleration respectively while the data-intensive block is executed on the end device for reducing data transmission latency.  3.2. Prediction stage  This stage has three main tasks: profiling execution latency, training latency prediction models, and utilizing latency predic- tion models. (1) Profiling execution latency. This task is to predicate the execution latency of each type of layer on different computing platforms. Since the execution latency is platform-dependent and type-dependent, the profiling process should consider different computing platforms and layer types. Specifically, four types of DNN layers are considered in the framework, namely convolu- tion (CONV), fully-connected (FC), activation (ACT), and pooling layer (POOL). Meanwhile, three different computing platforms (i.e., end devices, edge servers, and the cloud server) are taken into consideration in the task. (2) Training latency prediction models. The task is to train different neural networks on various computing platforms and layer types for layer-wise inference prediction. Since a DNN has limited types of layers, the training cost is moderate. In addition, we choose neural networks to build latency prediction models rather than linear models because the neural networks can learn well non-linear features related to execution latency.  •   For the prediction models of convolution and full-connected layers, we consider the input data size   d input   , the output data size   d output   , the size of input feature maps   f input   , the size of output feature maps   f output   , the memory speed of computing platform   m   ∈ { m end ,   m edge ,   m cloud } , and the computing ca- pability   c   ∈ { c end ,   c edge ,   c cloud }   of computing platform in the training process.  •   For the prediction models of activation and pooling layers, we consider the input data size   d input   , the input feature maps  f input   , the size of output feature maps   f output   , the memory speed of computing platform   m   ∈ { m end ,   m edge ,   m cloud } , and the computing capability   c   ∈ { c end ,   c edge ,   c cloud }   of computing platform in the training process. Since the output data size and the output feature maps of these two layers are equal to the input data size and the input feature maps respectively, the training data with two features are needed to construct for training these prediction models. (3) Utilizing latency prediction models. This task is to use trained latency prediction models to estimate the execution la- tency of each type of layers on different computing platforms.  425

Benchmark of computation partitioning algorithm  To evaluate the performance of our computation partition- ing algorithm, we compare our approach with the following partitioning strategy in different wireless networks.  •   End-only:   This is a local strategy, where the entire DNN computations are executed on an end device.  •   Edge-only:   This is an edge strategy, where the entire DNN computations are executed on the edge server.  •   Cloud-only:   This is a cloud strategy, where the entire DNN computations are executed on the cloud server.  •   End–edge:   This is a collaborative partitioning strategy, which is realization of Edgent [6]. Specifically, the strategy outputs the optimal one partitioning point, where the first block is executed on the end devices and the rest block is offloaded to the edge server for executions.  •   End–cloud:   This is an end–cloud computing paradigm, which is the realization of Neurosurgeon [20]. This strategy divides the DNN computations into two blocks, where the first block is assigned to be executed on the end device and the remaining block is offloaded to the cloud server for execution.  •   End–edge–cloud:   This is an end–edge–cloud collaborative partitioning strategy, which is a realization of [14,28]. The strategy leverages Deep Q-Network (DQN) to learn the op- timal partitioning decision (i.e., the computing platform to which each DNN layer will be assigned).  4.2. Conclusion  In this paper, we have presented an adaptive DNN inference acceleration framework to reduce DNN inference latency in the end–edge–cloud computing environment. In this framework, we first built latency prediction models based on neural networks for DNN layer execution, which provide a basis for DNN computation partitioning. Then, we designed a computation partitioning algo- rithm based on latency prediction results and network conditions for accelerating DNN inference, which divides DNN computations into end devices, edge servers, and the cloud server. Experimen- tal results show that our approach can effectively reduce the end-to-end inference of DNN-based intelligent applications and outperforms other baseline approaches. In future work, we will take into account how to coordinate the balance between latency and energy consumption in our framework for further accelerating DNN inference. In addition, a fine-grained DNN partitioning based on layer is needed to take into account.
